These establish unsafe interleavings, not ordinary awaited-call failures or their frequency. Awaiting rename before changing settings avoids that particular caller-created overlap.

Contract audit of CodeSDK 1.10.1 / Core 1.74.0 found no blanket requirement to serialize all Session methods or wait for idle. The [Session reference](https://mastra.ai/reference/agent-controller/session) guarantees ordering for concurrent state updates specifically. The [exact-release native TUI](https://github.com/mastra-ai/mastra/blob/b21e46e19b469a25c8896bcee90afd58d6f1a890/mastracode/tui/src/tui/mastra-tui.ts#L1277-L1337) allows settings/name commands during a run. [ACP](https://mastra.ai/reference/code-sdk/acp-server#sessions-and-mcp-servers) adds its own per-session prompt/config queue; that is adapter policy, not a universal Session contract. None of these establishes cross-domain atomic persistence.

Actual native local-LibSQL evaluations in `spikes/mastra-code-sdk/test/chat-concurrency-contract.test.ts`, across two fresh runs:

### Contingent native persistence repair scope (2026-10-08; not recommended on current evidence)

User requested concrete scope before accepting ongoing patched-dependency maintenance. Read-only audit of the pinned published source maps and actual native regressions finds a medium native repair: three packages (Core, Memory, LibSQL), roughly a dozen source files and an estimated several hundred source lines plus concurrency tests. This is a source-level estimate, not a completed patch. CodeSDK factory/integration and Kodex's product database need no change. No installed SDK files have been edited.

Preferred design: one native thread-mutation operation accepts a short synchronous, retryable function over the current stored row. Each writer composes only its own change from that fresh row. Omitted fields remain untouched; explicit metadata deletion and stored null must retain distinct semantics; missing rows are not recreated. Model calls, embedding, observation and event emission remain outside the operation. Committed before/after values govern native title events.

- **Core:** add the storage/domain mutation surface; migrate Session rename, controller setting set/delete, token usage and explicit title generation, plus the normal Agent automatic-title persistence path. Token usage must be read from the session inside each application attempt so an older pending save cannot restore older totals; do not use maxima because reset is legitimate.
- **Memory:** migrate the five thread-scope OM write boundaries (synchronous observation, buffered extraction, reflector extraction, buffered activation and manual reflection). Compose metadata and test `titlePinned` against the same current row before applying a generated title.
- **LibSQL:** provide atomic mutation and use it beneath existing partial thread/metadata updates without changing their merge contracts. First evaluate compare-and-swap: read exact title, SQL `json(metadata)` and resource identity, compute a pure update, then condition one autocommit UPDATE on those original values. A zero-row result rereads/recomputes with bounded retries. Do not compare `updatedAt`, which unrelated message writes change. This avoids schema/version migrations and synchronous local-client transaction contention. A transaction implementation is an alternative only after proving a shared gate across native handles; the product-store gate alone does not protect native storage.

Required proof: both demonstrated rename/settings and usage/rename races become preservation assertions; older/newer usage saves and reset; deletion versus null after reopen; OM/settings overlap; manual pin while an automatic/OM candidate is already pending; concurrent native handles and processes; deletion/missing rows, callback failure and retry exhaustion; committed events/readback; existing model/queue/OM regressions. CAS SQL representation, contention and bounded failure are unproven until that first experiment passes.

Bound this repair to Kodex's mounted thread-scope LibSQL configuration. Resource-scoped observation, legacy/network title writers, channels and thread-scoped working memory require explicit inventory before a universal upstream claim, as do other storage adapters. Creation/clone operations remain creation paths; message writes touching only timestamps are outside the metadata repair. Multiple independent session counter owners and detached writes after retirement are separate lifecycle limits. A generic mutex fallback must not imply cross-process atomicity.

Maintenance includes reproducible builds/patch application for three pinned packages, ESM/CJS/declaration checks, and re-auditing changed writer paths on upgrades. Injecting storage alone cannot distinguish stale fields from intended changes in existing whole-row callers; a gateway mutex misses native background writers. If representative failures later justify this approach, the implementation sequence would be: prove the LibSQL primitive first, repair Core and the two forced interleavings next, then migrate/test OM. Decide whether to maintain the complete patch from that reviewed result; no commitment to a permanent fork yet.
